# Site behaviour inventory

The niche, undocumented things. Each entry is a behaviour of a real page that a naive implementation
gets wrong, why it matters, and where the fix lives.

**Status column:** `code` means the handling exists and is exercised by the test suite where it is
testable; `live?` means it has **not** yet been confirmed against the real site in a browser; `live`
means it has, and the parenthesised part says when, on what, and what happened. Readings from
2026-10-08 come from the Firefox rig described under [The live rig](#the-live-rig) — a signed-in
profile copy, driven over its DevTools protocol, with the Remote Agent off.

## Cross-site mechanics

| # | Behaviour | Why a naive version breaks | Handling | Status |
| --- | --- | --- | --- | --- |
| 1 | **Rich editors ignore `element.value` / `textContent`.** ProseMirror (ChatGPT, Le Chat), Lexical, Quill (Gemini) keep their own model. | The text appears in the box but the framework never sees it, so the send button stays disabled or sends nothing. | `execCommand('insertText')` first, then a real `ClipboardEvent('paste')` with `DataTransfer`, then DOM write + `InputEvent`. Each attempt is verified by reading the box back. | code |
| 2 | **React-controlled `<textarea>` ignores a direct `.value` assignment.** Copilot, Grok, Qwen, DeepSeek. | React's `onChange` never fires; the button stays disabled; the prompt silently never sends. | Set the value through the **native prototype setter** (`HTMLTextAreaElement.prototype.value`) then dispatch `input`. | code |
| 3 | **Some send controls are not `<button>`.** DeepSeek's is a `div[role=button]`; Kimi's is a styled `div`. | `querySelector('button')` finds nothing and the send is reported as failed. | Adapters list `[role="button"]` candidates, and `send.mode: 'enter'` makes Enter the primary path with a click fallback. | code |
| 4 | **Enter inserts a newline in some editors** (Shift+Enter semantics vary per site). | The prompt sits in the box with a trailing newline and nothing is sent. | If Enter produces no send evidence within 5s, we click the button instead — and vice versa for click-first sites. | code |
| 5 | **The send button does not exist until the box has text.** ChatGPT and Gemini render it conditionally. | Looking for the button before inserting finds nothing. | Insert first, *then* resolve the button; the fallback heuristics run after insertion. | code, live (2026-10-08: the diagnostic found **no send control on any of the seven** sites with an empty box; all five sends that followed confirmed) |
| 6 | **The stop button appears only after the first token on some sites.** | Using "stop button present" as the send confirmation reports a failed send on a slow first token. | Three independent signals: stop button, box emptied, or answer length grew. Any one confirms. | code |
| 7 | **Long conversations are virtualised, so the DOM shrinks.** | A total-character measurement goes *down* when an old turn unmounts; a naive "changed ⇒ still streaming" test never concludes, and the answer times out. The opposite failure was measured live on DeepSeek: when an older turn unmounted *while the new answer was being painted*, the total on screen fell, the high-water mark never rose, and a 1322-character answer was recorded as 388 with the wait ending 2.6s after the press. | Length is tracked as a **high-water mark**. Only increases count as output; completion is judged against the peak. **Known limit, measured 2026-10-08:** the mark cannot see a new answer whose paint is masked by a simultaneous unmount — that case is open. | code, live |
| 8 | **A usage limit or human check can arrive mid-answer.** | The wait runs to the timeout and reports "no answer seen in time" — the least useful possible message. | Attention is re-checked on every tick while streaming, and a banner is a terminal state. | code |
| 9 | **Conversation text can mention limits.** | A conversation *about* rate limiting trips a naive text scan, so the extension warns that the AI is out of quota when it is fine. | Only banner-shaped containers are scanned (`[role=alert/dialog/status]`, `[class*=banner/toast/modal/captcha/challenge]`), never the message list. Pinned by a test. | code |
| 10 | **A login link can be visible while signed in** (sidebar, "switch account"). | Reporting "signed out" whenever a login link exists produces constant false warnings. | Login selectors are only trusted when the URL matches a login path, or when **no composer exists** at all. | code |
| 11 | **Our own insertion fires `input` events.** | Time you spent "writing" would be credited to the script, inflating the writing bucket on every broadcast. | A programmatic guard window suppresses tracker input during insertion. Signals are also required to be `isTrusted`. | code |
| 12 | **Sites keep the old text in the box on a failed send.** | Without clearing, the next prompt is appended to the previous one. | Every insertion selects the whole box first and verifies the read-back matches exactly. | code |
| 13 | **Single-page apps navigate without a page load.** | The content script never re-runs, so the tab looks dead after switching conversations. | An 800 ms href watcher re-sends `HELLO` and re-evaluates site status. | code |
| 14 | **Hidden tabs have their timers throttled to ~1/minute.** | "Waiting while you were elsewhere" is impossible to measure honestly from inside the page. | That one metric is measured in the **background**, which is not throttled: a 5 s sampler over live jobs. Content-side waiting is counted only while the tab has focus, so the two never overlap. | code |
| 15 | **A page's CSP can block an injected `<style>`.** | The in-page overlay renders unstyled — invisible text over the page. | A **constructable stylesheet** via `adoptedStyleSheets` (not subject to `style-src`), with a `<style>` fallback. | code |
| 16 | **Tabs opened before the extension loaded have no content script.** | The most recently used AI tab is the one most likely to be open, and it is exactly the one that would fail. | Ping → `scripting.executeScript` injection → ping again, with a one-retry send. | code |
| 17 | **Several tabs of the same AI.** | Duplicate "answers ready" rows for one conversation, and the wrong tab brought forward. | Newest answer per AI replaces older ones; the tab is chosen by `lastAccessed`; closing a tab drops its entry. | code |
| 18 | **An answer can finish before the first poll.** | Very fast answers never show a stop button and the "grew" signal fires late. | The quiet-period rule concludes a finished answer without ever needing the stop button. | code |
| 19 | **Sites remember a slow mode between visits.** See DeepSeek below. | Every broadcast answer is slow *and* the returned answer is not the standard one, so the head-to-head comparison is unfair. | Per-site toggles, off by default except DeepSeek; only clicked when the control reads as **on** (`aria-pressed`, `aria-checked`, active class). | partly live? |
| 20 | **The tab you started from is also an answer.** | Excluding it makes "fastest on shared prompts" compare only the AIs you did *not* type in, which is the wrong question. | Capture-phase `keydown`/`click` detects your own send, and joining the group means your own AI competes too. | code |
| 21 | **A prompt sent by hand is still a prompt.** | Only broadcast sends being timed leaves the dashboard's per-AI totals missing most of your real usage. | Manual sends are detected (trusted events only, box had text, evidence of a send) and timed identically. | code |
| 22 | **A session can end without the page's markup changing.** Sign out in another tab, an expired token, a revoked session: an app shell keeps drawing the same header and message box it drew while signed in, so the DOM says nothing at all. Reported from a Copilot tab that was signed out while the extension said it was signed in. | A sign-in check is a fact about a moment, and trusting it for a week means a prompt goes into a page that will never answer — the one failure that reads as our bug. | The stored check is not the last word: the ping every tab is already sent during warm-up carries the page's own live verdict, so a page that says it is signed out is refused before anything is typed, its check is cleared and the popup names the AI that needs you. A page that says it is signed in re-stamps its check, so the record describes this session rather than an older one. | code |
| 23 | **A sign-in control need not have any words in it.** Icon-only headers: a picture of a person whose *accessible name* is "Sign in", with an empty `textContent`. | A door scan that reads text alone finds nothing, so a signed-out page with a message box on it is reported as ready — the direct cause of the Copilot false "signed in". | The door scan reads `aria-label`/`title` first and `textContent` second. Labels that belong to a signed-in session (an account menu) are pinned by a test so they cannot become false warnings. | code |
| 24 | **A signed-out wall is not always there yet.** These apps are server-rendered signed-out chrome that a session replaces: the Sign-in control, and for Copilot the whole wall, are on screen while the account handshake is still in flight. On a tab in a background window — every tab of an ordinary fan-out, and every tab of a broadcast on Firefox, where an unfocused window is throttled — the handshake can land seconds after the markup. Reported as three AIs reading "Signed out" while the user was signed in to all three, and it was sporadic because it depends on how fast the page wins the race. | One reading taken during those seconds cleared an AI's check and left it out of every send, with nothing to bring it back. | A signed-out verdict is confirmed before it is believed: the page is read again 1.5 seconds later and *that* answer is the one reported. A door still standing after the page has settled is a door; a door that was the loading screen is not a session. Nothing on the happy path pays for it — a page that is already fine is returned as read. | code, live (signed-out Copilot wall and kimi.ai doors inspected in a browser) |
| 25 | **A reading is not a fact about now, and the record said it was.** A site's status was written when something happened to it — its page loading, a failed send — and read by the popup as the present tense, so records from days ago were displayed as "Signed out". Worse, an off site's page goes dormant and stops running the check that would have corrected it, so the wrong reading was also the last one. | The panel told the user something untrue about their own browser, and the badge stayed quiet about it because `lib/badge.js` had already learned to forget. | The popup asks every AI that has a tab open what its page is showing, every time it is opened (one message per open tab, throttled to 20s; answers arrive as storage writes, so the switches redraw themselves). A flag older than the ten minutes the badge stops nagging at is history: it no longer keeps an AI out of a fan-out, and the row shows what is actually known — *closed* — with the old reading in its tooltip. A page that says it is fine restores the check the bad reading cleared. | code, live (popup driven in Chromium) |
| 27 | **An answer can arrive in one response and be painted in afterwards.** DeepSeek's whole answer comes back in a single response of about a second — 1078 bytes for a 1277-character paragraph — and the page then types that text in over the following seven, so for most of the wait the text on screen is still growing while the network is finished and quiet. | A closed stream was taken as the end: the panel said *Ready after 2.8s* about an answer nobody could read yet, the job card called it finished while the page was still writing, and the event recorded **619 of its 1277 characters**. The recorded answer was half an answer, and the number next to it was not a time anybody waited. | A closed stream is the server's half of it. The network path now also requires the text on screen to have stopped growing, and the recorded time is the moment the *last character appeared*, which on an ordinary site is the same instant as the stream closing. Live, DeepSeek, 2026-10-08: recorded 1289 characters against 1289 on the page, *Ready after 3.6s*; pinned by `tests/watcher.test.mjs`, which fails without the rule. | code, live |
| 26 | **A count of what a send reaches has three terms, and one of them is a tab.** The panel's *Goes to X of Y* counted switched-on and signed-in, while the send itself skipped a signed-in AI with no tab open (`no tab open`, the default since tabs stopped being opened for it) — and the row beside the count said *closed*, so the panel was disagreeing with itself on one line. | A number the user is asked to trust is a promise about what pressing the button does; a promise wider than the send is how the button starts to look broken, and it is tilted the wrong way — it over-promises in exactly the state the tab switch below it is about. | The reach is the same conjunction the engine enforces a moment before it types: switched on, signed in, and — while *Open a tab for AIs you have not opened* is off — already open. One rule and one sentence in `lib/reach.js`, read by the popup's summary and by the launcher's pill, card header, row text (*closed* beside *signed in*) and tooltip. The tab term is the one a content script cannot see for itself, so the background answers a page that asks (on boot, and when it comes back into view) and pushes to the open AI pages when that set changes. | code |

## The live rig

Live readings come from a **copy** of a signed-in Firefox profile (`scripts/restart-firefox.sh`),
with the built extension installed into it and driven over the DevTools protocol
(`scripts/rdp.mjs`), plus WebDriver BiDi where it is useful (`scripts/bidi.mjs`). Two properties of
that rig are part of the readings above, and both were found the hard way:

- **The Remote Agent is off** (`WF_BIDI_PORT=`). Starting it is what makes Firefox answer
  `navigator.webdriver === true` on every page, and with it on, chatgpt.com, claude.ai and
  perplexity.ai answered **"Just a moment..."** — Cloudflare's challenge — instead of the app, while
  the extension sat on a page that was not the page a user gets. A rig holding that port open is
  testing a browser nobody has.
- **The window is not focused**, which is both the ordinary state of a fan-out's tabs and the state
  Firefox throttles hardest — timers in a background tab, and an unfocused window's whole tree, are
  slowed or stopped. The two anomalies above (Grok, Gemini) appeared in long-lived unfocused tabs and
  not in fresh ones, which is why "the page had the answer and the extension did not see it" is filed
  as starvation until it is reproduced with the window focused.
- **The event page sleeps, and `bg` probes then do nothing quietly.** `node scripts/rdp.mjs bg …`
  evaluates its expression in every frame the add-on has. Once the background page has been unloaded
  for idleness the only frame left is Firefox's `webextension-fallback` document — which has no
  `browser` — so the probe prints `undefined` and runs nothing at all, which looks exactly like a
  probe that ran and found nothing. Any content-script message wakes the page; do that first when a
  `bg` reading comes back empty or a fresh browser is being driven:
  `node scripts/rdp.mjs eval deepseek "WF.browser.send({ type: WF.MSG.SITE_STATUS, siteId: 'deepseek', attention: null, hasComposer: true, url: location.href }); 'woke'"`.
- **A session can be carried into the copy.** The copy is what makes the rig safe to restart, and it
  is also why a site can read as signed out: it was made before the sign-in. DeepSeek's was fixed by
  copying the real profile's `cookies.sqlite` (checkpointed out of its WAL first, since the browser
  was running) and `storage/default/https+++chat.deepseek.com/ls/data.sqlite` over the copy's — its
  session lives in `localStorage.userToken`, not in a cookie, so the storage directory is the part
  that matters. The site had been listed here as untestable for exactly that reason.

## Verification

Per site, about five minutes:

1. Load the extension, open the site, sign in.
2. Toolbar icon → **Check this tab's markup**. All four lines should be populated:
   `composer`, `send`, `stop button`, `answers`. Anything saying `NOT FOUND` is a selector to fix.
3. Type a short prompt, press **Ask all** in the launcher. The other AIs should receive it, and this
   site's own send should still be yours to press.
4. Confirm the in-page list shows `first, Xs` on the winner and `answered in Xs` on the rest, and the
   badge count matches the number that landed.
5. For a site with a slow mode (DeepSeek above all): switch the mode **on** by hand, then broadcast
   again and confirm it was switched off before the prompt went in. That is quirk #19, and it is the one
   with the least confidence behind it.

If a step fails, the diagnostic text from step 2 is the whole bug report. Open an issue with it;
a fix is usually a single line in `src/lib/sites.js`.
